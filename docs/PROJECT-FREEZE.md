## 1. 凍結理由

### 1-A. 測定結果と体感の乖離

| 指標 | 結果 |
|---|---|
| 数値パリティゲート（`docs/parity-targets.md`） | **14/14 合格** |
| 操作シナリオ（`tests/scenarios/`） | **28/28 合格** |
| 自動テスト全体 | 598 passed（+1 expected fail） |
| **ユーザーの実プレイによる体感再現度** | **約3割** |

測定上はほぼ満点でありながら、体験としては原作の3割しか再現できていない。
この差は「あと少し詰めれば埋まる」性質のものではなく、**測定と体験の間に構造的な断絶が
ある**ことを意味する。

### 1-B. 失敗の主因は「正解が分からないこと」ではなかった

24周目で発見・修正した項目を振り返ると、失敗の性質が明確になる:

| 項目 | 正解はどこにあったか | なぜ落ちていたか |
|---|---|---|
| ボールの影が無い | 参照動画に明確に映っている | 描画コードのα二重掛けバグ。**検証項目に無かった** |
| スローインがキックイン | 公式説明書に「スローイン」と明記、動画にも投げる動作 | キック経路を流用した実装のまま。**検証項目に無かった** |
| キーパーが弾かない | 公式説明書に「パンチングは必ず弾く」と明記 | simは区別していたが描画が無反応。**検証項目に無かった** |
| スライディングで奪えない | 競技規則・原作挙動ともに明白 | 成功条件が背後コーン限定。**検証項目に無かった** |
| カメラが引きすぎ | 原作実測値が `docs/screen-geometry.md` にあった | 横長化の際に俯角だけ保存し可視範囲を見落とした。**検証項目に無かった** |

**すべて、正解が既に判明していた項目である。** 公式説明書・参照動画・ユーザー指摘の
いずれかに答えがあったにもかかわらず、実装で落ちるか、検証項目に入らず見落とされた。

したがってボトルネックは**情報の不足ではなく、「判明している正解を実装に反映し、
それを検証項目として保持し続ける」プロセスの側**にある。

### 1-C. この構造は測定精度を上げても変わらない

エミュレータ・イン・ザ・ループ・ハーネス（24周目-7で実現可能性を調査、成立と判定）は
**測定精度の問題を解決する**手段である。しかし上記1-Bのとおり、失敗の主因は測定精度では
なかった。**より正確な数値をより多く得ても、「検証項目に入っていない項目は見落とされる」
という構造は変わらない。** よって機材購入を見送り、プロジェクトを凍結する。

### 1-D. 収束見込み

現在の開発ループ（実装 → 自動ゲート → ユーザーの実プレイで不具合発見 → 修正）では、
体感3割から実用水準まで持っていくのに**年単位を要する**と判断した。

## 2. ★最重要★ 判明した構造的教訓（再開時に最初に読むこと）

本書で最も価値のある部分。24周目という1周期を丸ごと費やして得られた知見である。

### 2-1. 数値パリティの合格は、体験の再現を意味しない

**14/14 合格の状態で、ユーザーの体感再現度は約3割だった。**

数値ゲートが測っているのは「部分指標が原作の帯に入っているか」であり、
「それらの合成として立ち現れる体験が原作と同じか」ではない。

実例: ドリブルの物理速度は T1ゲート（2.15身長/秒）に合格していた。しかし
**カメラの可視幅が選手35.7人分（原作は9人分）だったため、画面上の移動速度は原作の約1/4**
で、「ドリブルが遅い」という体験になっていた。物理も框も個別には測っていたが、
**その合成である「画面上でどう見えるか」を測る指標が存在しなかった。**

→ CRITIC.md 原則8として明文化済み。再開時もこの原則を維持すること。

### 2-2. 測定項目に入っていないものは、永久に直らない

影の欠落・スローイン・キーパー・スライディングは、いずれも**何サイクル回しても発見され
なかった**。理由は単純で、**測定対象として定義されていなかった**からである。

自律開発ループは「定義された指標を緑にする」ことしかできない。指標の外にある欠陥は、
ループを何周させても発見されない。**ループの品質の上限は、指標の網羅性で決まる。**

### 2-3. 定性差分監査は、機能した唯一の工程である

`docs/visual-behavior-audit.md`（24周目-6で構築）は、この構造に対する唯一の有効打だった:

- **1回の実施で16件を台帳化**（ユーザー指摘7件 + 自発的に発見した9件）
- **カメラ可視幅35.7人分（原作9人分）という致命的欠陥を発見**した。これは体感全体を
  支配する最大の欠陥だったが、それまでの全サイクルで一度も検出されていなかった
- 「原作の該当場面のフレーム列」と「自作の同一場面のキャプチャ列」を並べ、
  物体・挙動・カメラ・演出・時間の5観点で差分を列挙する、という手順そのものが効いた

**再開時はこの工程を起点にすること。** 数値ゲートから始めてはいけない。

### 2-4. ユーザーが不具合の発見者になっている限り、収束しない

24周目を通じて、重大な欠陥の発見者は一貫してユーザーだった。開発ループ側は
「全ゲート合格」を報告し続け、ユーザーが実プレイして初めて欠陥が判明する、という
サイクルを繰り返した。

**この構造を変えられなかったことが、凍結の直接原因である。**

定性差分監査はこれを変えうる工程だったが、導入が遅すぎた（24周目-6）。しかも
1回の実施で16件が出たという事実は、**まだ観察されていない差分が相当数残っている**
ことを強く示唆する。

### 2-5. （前回凍結から継続）画面が「それっぽくない」ときは、まず俯角・カメラを疑う

20周目に `NEAR_WIDTH_RATIO` の1定数変更（俯角45°→16.7°）だけで「原作に全く見えない」
問題の大半が解決した。24周目-6でも、体感を最も支配していたのはカメラの可視範囲だった。
**2周期にわたって、最大の効きどころは常にカメラだった。**

### 2-6. （前回凍結から継続）選手スプライトは16x16では原理的に2頭身にしかならない

素材を探すときは「全高24〜32px以上」を最初の絞り込み条件にすること。

## 4. 見送った選択肢と、その理由

### 4-A. エミュレータ・イン・ザ・ループ・ハーネス（見送り）

  Lua入力注入 + FFV1ロスレス60fpsダンプで、「同じ入力→同じ結果」の検証が可能
- **見送り理由**: 1-C のとおり、**これは測定精度の問題を解く手段であり、
  失敗の主因（判明している正解が実装・検証に反映されない）を解かない**

**ただし価値が無いわけではない。** 再開後、体感が一定水準に達し「これ以上は測定精度が
最後のボトルネック」という段階になったら、着手する価値がある。設計書は完成しているので、
そのとき機材を買えばよい（設計のやり直しは不要）。

### 4-B. ゼロからの再実装（不採用）

蓄積した原作実測値・落とし穴の知見（決定論の守り方、AIしきい値の相互作用、
バタフライ効果への対処手順など）を失うため、**全面的な作り直しは不採用**。

**ただし部分的な選択肢としては有効**: 再開時に
**`CLAUDE.md` / `docs/parity-targets.md` / `docs/visual-behavior-audit.md` / `CRITIC.md`

## 5. 再開する場合の推奨順序（前回から全面更新）

**大原則: 数値ゲートから始めてはいけない。台帳（定性差分監査）から始める。**

1. **台帳の全項目を洗い直す** — `docs/visual-behavior-audit.md` の「中」6件・「低」2件を
   含めた全16件を再点検し、さらに**新しい差分を探す**。1回の監査で16件出たという事実は、
   まだ観察されていない差分が相当数あることを意味する（2-4）。
   特に未観測の場面（コーナーキック、カード/退場、試合前後の演出）を優先
2. **台帳を起点に、体感再現度を上げることのみを目標に修正する** — 数値ゲートは
   「壊していないこと」の確認に留め、**目標にしない**（2-1）。
   各修正の後にユーザーの実プレイ確認を挟み、体感の変化を直接測る
3. **体感が6〜7割に達した段階で、精度の最終調整としてエミュレータハーネスを検討する**
   （4-A。設計書は完成済み、機材を買えば7〜11日で構築できる）
4. **AI調整（段階4）は最後** — CPU/味方AIの質は、操作と見た目の手触りが固まってからでないと
   評価できない（前回凍結からの継続方針）。統計ゲートの停滞項目 c6 もここで扱う

## 6. 再開の外部条件（判断材料として記録）

**AIの動画理解能力の向上が、本プロジェクトの最大のボトルネックを解消しうる。**

本プロジェクトの構造的ボトルネックは **観察の網羅性**である（2-2, 2-4）。
現状、原作動画からの差分抽出は「フレームを切り出して人間/AIが目視で比較する」という
手作業であり、1回の監査で16件を挙げるのが限界だった。網羅性は担保できていない。

**もし「原作のプレイ動画をそのまま入力し、自作のプレイ動画と突き合わせて差分を
自動的に列挙させる」ことが実用水準になれば、このボトルネックは構造的に解消される。**
具体的には:

- 長時間の動画を通しで観察し、差分を漏れなく列挙できる（人間の集中力の制約を受けない）
- 「測定項目に入っていないから見落とす」（2-2）という失敗が原理的に起きなくなる
- ユーザーが不具合の発見者である構造（2-4）が解消される

**再開判断のトリガー**: 動画を直接入力して意味のある差分指摘が得られるモデルが
利用可能になったとき。そのときは、台帳（`visual-behavior-audit.md`）の形式をそのまま
出力先として使えるので、本プロジェクトの資産はすべて活きる。

## 8. このプロジェクトの目的（再開時に思い出すこと）

**北極星: 「スルーパスが通った瞬間が最高に気持ちいいこと」。**

操作はシンプル、判断はすべてプレイヤーに委ねる。市場調査の結論:
カジュアル系は判断ごと自動化し、ハードコア系は操作精度が競技になっている。
**「シンプル操作 × フル判断 × 俯瞰視点」の組み合わせは現行市場に存在しない。**

細部に迷ったら「この変更はスルーパスを狙う楽しさを強めるか弱めるか」で判断する。
