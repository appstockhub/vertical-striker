## 0. 結論（実現可能性調査の判定）

**成立する。** 判定基準との照合:

| 基準 | 判定 | 根拠 |
|---|---|---|
| (a) 技術的に成立するか | **成立** | BizHawkはTAS用途で決定論再生が実証済み（bk2ムービー=フレーム単位入力ログ+同一コア/設定で同一結果）。Lua APIで入力注入(`joypad.set`)・フレーム制御(`emu.frameadvance`)・キャプチャが可能。CLIに `--movie` `--lua` `--dump-type=ffmpeg --dump-name --dump-length`（FFV1ロスレス60fpsダンプ）がある。真のヘッドレスは不可だが、**ウィンドウ表示ありの自動実行で要件は満たせる**（可視ペインで起動→CLI+Luaで無人運転） |
| (b) 構築工数 ≤ 2週間相当 | **満たす** | 見積 7〜11日（下記9節）。既存資産の再利用が効く: 60fps無圧縮キャプチャに対して `scripts/video/`（追跡・指標算出）がそのまま適用でき、sim側の対照実行系は既存のシナリオハーネス(`tests/scenarios/harness.ts`)の流用 |
| (c) 法的リスク | **運用で管理可能** | 自己所有カセットの私的複製・非配布・クリーンルーム原則・リポジトリ非コミットの機械的強制を `docs/rom-capture-policy.md` に明文化済み。SFCカセットの読み出しに保護手段の回避は伴わない |

## 1. 全体構成

```
[原作カセット] --(吸い出し機/ユーザー実施)--> [ROM (リポジトリ外)]
                                                  |
        +------------------ 入力スクリプト (JSONL、リポジトリ管理) ------------------+
        |                                         |                                  |
        v                                         v                                  |
[A. 再生系: BizHawk]                    [B. 対照実行系: 自作sim]                      |
  Lua注入 or bk2ムービー                  scripts/parity/runScript.ts                 |
  --dump-type=ffmpeg (FFV1 60fps)         (シナリオハーネス流用、状態を直接JSONL出力)  |
        |                                         |                                  |
        v                                         v                                  |
  [emu-capture.avi]                       [sim-trace.jsonl]                          |
        |                                         |                                  |
        +----------> [C. 差分系: scripts/parity/compare.py] <------------------------+
                       emu側: scripts/video/ の追跡を60fps無圧縮に適用
                       sim側: トレースを直接読む
                       → 指標対比表 + パリティ判定 (PASS/FAIL/許容帯)
                       → docs/parity-targets.md の「実測値」列を更新
```

## 2. 実行環境

| 環境 | 再生系 | 備考 |
|---|---|---|
| **DAIV (Windows) — 正本** | BizHawk (EmuHawk) + BSNESコア | Luaは Windows 版でフル対応。ハーネスの正本環境はこちらに一本化する |
| Mac — 補助 | Mesen 2 (Win/Linux/macOS対応、Lua APIあり) | BizHawkはmacOS非対応(Wine経由は非推奨)。Macで作業したい場合の代替だが、**計測の正本はBizHawk/Windowsに固定**し、環境差の混入を避ける |

- コアはBSNES系（サイクル精度）を使用し、コア名・バージョン・SyncSettingsを
  計測メタデータとして全キャプチャに記録する（決定論の前提条件）
- 60fps無圧縮の根拠: 現行手法の敗因（30fps・圧縮・VFR・実効fps 37〜47）を全て潰す

## 3. 入力スクリプト形式（正本）

リポジトリ管理する正本は**機種非依存のJSONL**とし、両系へ変換して与える:

```jsonl
{"f": 0,   "dpad": "Up",   "btn": ["B"]}
{"f": 1,   "dpad": "Up",   "btn": ["B"]}
{"f": 30,  "dpad": "None", "btn": []}
```

- `f`: フレーム番号（60fps基準）。記載のないフレームは直前の状態を保持（ランレングス）
- `dpad`: 8方向 + None（自作simの `Direction8` と同名）
- `btn`: SFC論理ボタン `B/Y/A/X/L/R/Start/Select` の押下集合
- 変換系:
  - → BizHawk: Luaスクリプトが JSONL を読み、毎フレーム `joypad.set` で注入して
    `emu.frameadvance()`。または bk2 の Input Log へ変換して `--movie` 再生
    （長尺・完全再現用。bk2はzip内のプレーンテキスト入力ログなので生成は容易）
  - → 自作sim: `Inputs`（direction + ButtonState）へ1:1マップし、
    `simulate()` を同フレーム数だけ回す
- シナリオはドリル型を基本とする: 「キックオフ→N歩前進→B溜めMフレーム→解放」のような
  **短い合成シナリオ**を積み上げる（試合全体の再現はAI差により不可能 — 7節参照）

## 4. 比較する指標

| 系 | 指標 | emu側の取得 | sim側の取得 |
|---|---|---|---|
| ボール物理 | 位置系列 / 初速 / 転がり摩擦 / 弾道高さ / 滞空時間 / バウンド減衰 | `scripts/video/trackBall.py`（60fps無圧縮でVFR・重複フレーム問題が消滅） | トレースJSONL（`ball.pos/vel/height`） |
| 操作応答 | 入力→キック発生までのフレーム数 / 溜め時間と初速・弾道の対応カーブ / タックル・チャージの発生と持続 | 入力スクリプトのフレーム番号と画面上の変化の差分 | イベントログ（`lastEvent`・速度ジャンプ） |
| 選手挙動 | 走速 / ドリブルタッチ周期・ギャップ / スライド距離と時間 | テンプレート追跡 + 手動アノテーション併用 | トレースJSONL |
| カメラ | 画面内ボール位置 / スクロール速度 / 先読み挙動 | 背景特徴点の移動量（`trackBall.py` の cam_dx/cam_dy 実装済み） | `viewMetrics` / カメラ純関数 |
| アニメーション | ポーズ遷移のフレーム数（キックモーション・ダイブ・投げ） | フレーム送りの目視カウント（自動化しない: 少数で足りる） | 定数（`KICK_WINDUP_TICKS` 等） |
| 演出 | バナー表示時間 / 暗転・カットのタイミング / リスタートの「間」 | フレーム番号の差分 | 定数・イベントログ |

- すべて既存の正規化規約（選手身長=1、60fps tick）に載せる。**遠近の系統誤差±40%は、
  同一地点で繰り返すドリル型シナリオ+既知寸法の校正で±数%まで縮む見込み**
  （固定カメラ距離のドリルを選ぶことで遠近補正を定数化できる）

## 5. パリティ判定の基準

1. **指標ごとの許容帯**: `docs/parity-targets.md` の各行を「動画推定値」から
   「エミュ実測値」へ置換し、許容帯を再設定する（原則: 実測の±10%、
   離散量子化が絡むものはtick単位の完全一致を狙う）
2. **シナリオ単位のPASS/FAIL**: 1シナリオ = 1入力スクリプト + 期待指標の組。
   `tests/scenarios/` のラチェット方式を踏襲し、合格したシナリオは回帰ゲート化する
3. **段階制**: 第1弾はボール物理（キック初速・摩擦・弾道・バウンド）→ 第2弾は操作応答
   （溜めカーブ・ワインドアップ）→ 第3弾はドリブル・タックル → 第4弾はカメラ・演出。
   AI挙動はパリティ対象にしない（7節）

## 6. 既存の批評役・台帳との統合

- `docs/parity-targets.md`: 「原作実測値」列の出典を `E:`（エミュ実測、入力スクリプト名+
  フレーム範囲）で表記する。動画由来の値(`V:`)と区別し、E階級を正とする
- `docs/visual-behavior-audit.md`: 台帳の「原作の正解挙動」のフレーム引用を、順次
  エミュ実測（再現可能な入力スクリプト付き）へ格上げする。新しい場面（コーナーキック等、
  参照動画に無かったもの）はエミュで**能動的に発生させて**観察できるようになる
- `CRITIC.md` / 批評役: 判定手順に「E階級の実測が存在する指標は、E階級との照合を必須と
  する」を追加する。批評役は入力スクリプトを自分で再生して数値を再現できる
  （= 実装者の申告に依存しない、再現可能な検分）
- ROM衛生の検分: 批評役の確認項目に「ROM系ファイルが staged/コミットされていないこと」を
  追加する（rom-capture-policy.md 4節）

## 7. これで解決できる問題 / できない問題（正直な列挙）

### 解決できる

- **数値の確度**: 30fps圧縮動画の±40%系統誤差 → 60fps無圧縮+入力既知で±数%〜tick一致
- **入力条件付きの挙動**: 「Bを何フレーム押すと何が起きるか」を初めて直接計測できる
  （現行手法では入力が観察できず、挙動の原因が推測だった）
- **再現性**: 同じ入力スクリプトを何度でも再生でき、批評役が独立に検証できる
- **未観測場面の能動的生成**: コーナーキック・ファウル・PK等、参照動画に無い場面を
  意図的に発生させて観察できる
- **アニメーション・演出のフレーム精度**: ポーズ遷移・バナー時間・「間」の正確な計測

### 解決できない（明確にしておく）

1. **試合全体の同一再現は原理的に不可能**: 「同じ入力→同じ結果」は各システムの内部でのみ
   成立する。原作のAI（10人の味方+11人の敵）と自作のAIは別物なので、同一入力列を与えても
   試合展開は一致しない。**ハーネスの単位は短いドリル型シナリオ**（操作選手+ボールが
   支配的な場面）であり、AI挙動のパリティは対象外（AIは従来どおり観察に基づく設計項目）
2. **内部状態は見えない**: 観察できるのは画面のみ（クリーンルーム原則によりメモリ解析は
   しない）。「見かけ上同じ」以上の同一性は証明できない
3. **素材は作れない**: スプライト・音の見た目/聞こえ方の観察はできるが、成果物の
   アセットは引き続き自作/CC0のみ（クリーンルーム）
4. **手触りの最終判定は人間**: 数値が一致しても「体感が同じか」はユーザーの実プレイ判定が
   最終ゲートであることは変わらない（CRITIC.md 原則8）
5. **エミュ自体の忠実度**: BSNES系コアは高精度だが実機ではない。実機差が疑われる事項が
   出た場合はその旨を記録する（実機検証はスコープ外）

## 8. 実装ステップ（機材到着後）

1. **P0 吸い出しとROM検証** (0.5日): ユーザーがダンパーで吸い出し → チェックサム確認 →
   BizHawkで起動確認。ROMはリポジトリ外へ配置
2. **P1 再生系** (1〜2日): BizHawk導入、Lua入力注入スクリプト（JSONL読取→joypad.set→
   frameadvance→終了フレームでダンプ停止）、`--dump-type=ffmpeg` FFV1 60fpsダンプの
   バッチ化（PowerShellラッパ）。決定論の自己検証（同一スクリプト2回→フレームハッシュ一致）
3. **P2 対照実行系** (1〜2日): JSONL→`Inputs`ローダ、`scripts/parity/runSimScript.ts`
   （既存シナリオハーネス流用、毎tickの状態をJSONL出力）
4. **P3 差分系** (2〜3日): `scripts/video/` を60fps無圧縮入力に対応させ（VFR処理の除去で
   簡素化）、`scripts/parity/compare.py`（指標算出・対比表・判定）を新設
5. **P4 パリティ第1弾** (2〜3日): ボール物理シナリオ5本（無溜めB・最大溜めB・Y/A/Xパス・
   ゴールキック・スローイン）で parity-targets のT2/T4/K2/P1をE階級化。批評役の
   判定手順を更新
6. 以後、台帳・ゲートの運用に組み込み（周次サイクルの一部になる）

## 10. リスクと未確定事項

- **BizHawkは真のヘッドレス不可**: ウィンドウ表示ありでの自動実行になる。開発環境の
  可視ペインで運転する運用（現行のブラウザ検証と同型）で吸収できる見込みだが、
  P1で最初に検証する（決定論の自己検証と併せて実装の第一関門）
- **Luaからの画面キャプチャ性能**: 毎フレームPNGは遅い可能性 → 正本はFFmpegダンプ
  (`--dump-type=ffmpeg`) とし、Luaは入力注入と制御に限定する
- **カセットの作品特定**: 参照動画・続編説明書と同一作品のカセットを購入する必要がある
  （ユーザーが特定済みの作品名で購入。初代も安価なので併せて購入推奨 —
  初代/続編の仕様差の検証にも使える）
