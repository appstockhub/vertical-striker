# ビジュアル手法転換の提案（調査・提案のみ。実装前にユーザー判断を仰ぐ）

作成: 2026-08-16。ユーザー指示
「ビジュアルが原作に全く寄っていない。コードで図形を組み合わせてスプライトを生成する現在の
手法には限界があると判断する。手法自体を変えたい」への回答。

**この文書は提案までで、実装は一切行っていません。**

---

## 0. 結論（先に）

**スプライトを差し替えるだけでは原作に寄りません。** 原因は3層に分かれており、
影響が大きい順に「① レンダリングパイプライン → ② パレット → ③ スプライトの絵柄」です。
現在の議論は③だけを見ていますが、①②を放置したまま③に良い素材を入れても
「高解像度でなめらかに描かれた、綺麗だが16bitに見えない絵」にしかなりません。

| 層 | 現状 | 原作 | 影響度 | 実装コスト |
|---|---|---|---|---|
| ① 描画パイプライン | 480x720、アンチエイリアスON、float座標、ベクター描画 | 256x224、ドット等倍、整数座標 | **最大** | 中 |
| ② パレット・色設計 | 暗い青緑 (輝度82)、平坦3色、遠方を**暗く**する | 明るい黄緑 (輝度151)、多数の中間色でディザ、遠方を**明るく**する | **大** | 小 |
| ③ スプライトの絵柄 | ベクター図形の組み合わせ | ドット絵 | 中 | 大（素材調達 or 外注） |

## 1. 実測による診断

原作スクリーンショット（256x224 ネイティブ）と自作キャプチャから、同じ領域の頻出色を
実際に抽出して比較した（`scratchpad/pngsample.mjs` で PNG をデコードして集計）。

### 1-1. 色の実測比較

| 領域 | 原作の頻出色 | 自作の頻出色 | 評価 |
|---|---|---|---|
| 芝（手前） | `#83b453` `#76ae4d` `#7bae58` … | `#237943` 75% / `#1c6636` 24% | **輝度が約半分**（151 vs 82）。原作は明るい黄緑、自作は暗い青緑 |
| 芝（遠方） | `#9acd6c` `#8fc765`（手前より**明るい**） | `#1a6033`（手前より**暗い**） | **空気遠近が逆向き** |
| 芝の色数 | 19x24px の領域に多数の中間色 | 手前は**わずか3色** | 質感（ディザ/ノイズ）が皆無 |
| 観客席 | `#c9dbdb` `#c5d5d4` `#c14931` `#ffffff` | `#0d1622` **100%** | 原作は明るい群衆、自作は**単色の黒帯** |
| HUD帯 | `#e7e7e7`（明るいグレー） | `#070b11`（ほぼ黒） | 明暗が逆 |

**芝の輝度**: 原作 (125,177,83) → 150.8 / 自作 (32,112,60) → 82.1（**54%**）。
原作は「晴天のデイゲーム」、自作は「ナイトゲームの暗いピッチ」に見えている。

### 1-2. 芝の縞の向き 【2026-08-17 訂正】

~~原作は縦縞（ゴールとゴールを結ぶ方向＝長辺方向）で、遠近法で消失点へ収束していく。
自作は `STRIPE_DEPTH` によるY方向の帯＝横縞で、向きが90度違う。~~

**この診断自体が誤りだった。** V-4実装後にユーザーが実機(GitHub Pages)で確認した結果、
「原作の縞はピッチを横切る方向（タッチラインと平行、奥行き方向に交互に切り替わる帯）」
であり、当実装の元々の `STRIPE_DEPTH` によるY方向分割の方が正しかったと判明した。
X軸分割への変更は撤回し、Y軸分割へ差し戻した (HANDOFF.md 22周目)。

### 1-3. スタンド・広告板

原作は「明るい群衆（白・水色・赤の細かいドット）＋ 白系の広告板の帯」で、
画面上部が情報量豊かに埋まっている。自作は暗い青灰の段＋わずかなドットで、
しかも段階1で追加した遠方のかすみ（暗色オーバーレイ）が上に乗って**ほぼ黒一色**に潰れている。

### 1-4. ゴールネット

原作は密なメッシュ（縦横とも細かい格子）でネット面がはっきり見える。
自作は縦4本＋横2本の最小限で、ネットというより枠線。

### 1-5. 参考画像の限界（正直な注記）

収集した原作画像は拡大・再圧縮を経ており、19x24px の領域から349色が検出された。
本来のSNESスプライトは15色以内なので、**この画像から原作の正確なパレットやドットは復元できない**。
色の「クラスタ中心」（芝が #7db153 前後、など）は信頼できるが、
ピクセル単位の模写はできないし、そもそも原則上してはならない。

### 1-6. 【重要な訂正】段階1の「ピッチが細すぎる」結論は、描画パラメータ1つで解ける

段階1で「ピッチが選手に対して約3.6倍細い。直すには `PITCH_WIDTH` を 480→1200 に変える
（＝AIしきい値の全面再調整が必要）」と報告しましたが、**これは誤りでした。訂正します。**

「ピッチが選手の何人分の幅か」は、**選手の“描画上の”大きさ**との比です。選手の描画サイズは
sim ではなく描画層の定数で決まるため、**`nearWidthRatio`（投影の横方向スケール＝実質カメラ高さ）
を変えるだけで、sim を一切触らずに原作の比率にできます。**

`nearWidthRatio` を振ったときの解析値（`focal = R × nearDepth`、`camHeight = (H − horizonY) / R`）:

| nearWidthRatio | カメラ俯角 | ピッチ幅=選手何人分 | 画面内に見える選手数 |
|---|---|---|---|
| **1.18（現状）** | **45°** | **8.3** | 11.5 |
| 3.00 | 22° | 21.1 | 11.5 |
| 4.00 | 17° | 28.1 | 11.5 |
| **5.00** | **13°** | **35.2** | 11.5 |
| 原作（実測） | **15〜22°** | **約34.5** | 約9 |

3つの重要な点:

1. **「画面内に見える選手数」は R を変えても 11.5 のまま**（＝プレー体験の密度は変わらない）。
   選手の画面上の大きさは `nearDepth/depth` で決まり R に依存しないため、
   R を上げるとピッチだけが大きくなり、相対的に選手が小さくなる
2. **現状のカメラ俯角は45°** で、原作の15〜22°よりはるかに**急**だった。
   段階1では「画角は一致している」と報告しましたが、一致していたのは画面上の量（可視範囲・
   選手サイズ）であって、**カメラの角度は一致していませんでした**
3. R≈4〜5 で、俯角・ピッチ比率がともに原作の実測値に収まる

**帰結: 段階4の冒頭に確定させた「ピッチ幅を1200へ変更＋AIしきい値の全面再調整」(D-1) は、
不要になる可能性が高い。** まず `nearWidthRatio` を上げて確認すべきです。
定数1つの変更で、`src/sim/` は無変更、AIの再調整も不要です。

副作用（要判断）: R を上げると、ボール位置で画面に写るピッチ幅が 667px → 約200px に狭まります。
横に広がった味方は画面外に出ますが、**原作も同じ**（原作は幅68mのうち約17.7mしか見えていない）で、
その視野の狭さをレーダーで補うのが本作の設計です。

**この訂正は解析値であり、まだ実際に描画して確認していません。** 実装前の検証として、
`nearWidthRatio` を変えたキャプチャを撮って原作と並べることを提案します。

## 2. 手法転換の選択肢

### 案A: 低解像度レンダリング + ドット等倍拡大（最も原作に近づく）

ゲーム画面を**低解像度の内部バッファ**（例 240x360）に描き、
ニアレストネイバーで2倍に拡大して 480x720 として表示する。

- Phaser 側: `pixelArt: true`（アンチエイリアスOFF + roundPixels）、`width/height` を低解像度に
- **必要な前提改修**: 現在 `PITCH_WIDTH = VIEWPORT_WIDTH` とピッチの論理幅が画面幅に直結している
  （`src/config/pitch.ts`）。ここを切り離し、「ワールド寸法」と「レンダリング解像度」を独立させる必要がある
- 効果: **これだけで「16bitっぽさ」の大半が出る**。線も芝も選手も全部ドットになる
- 副作用: **HUDの日本語テキストが読めなくなる**（現在11〜13pxのテキストが11個。半分の解像度では5〜6px相当）

### 案B: ワールドだけ低解像度 + HUDは等倍（案Aの現実解）

ピッチ・選手・ボールなど**ワールドの描画だけ**を低解像度バッファに描き、
HUD（スコア・時計・ボタンガイド・ドリルパネル）は従来どおり480x720に重ねる。

- 効果: 案Aの見た目を保ったまま、テキストの可読性を維持できる
- コスト: 2つの描画レイヤーを持つ構成へ変更（Phaserの2カメラ構成 or オフスクリーンcanvas）
- **私の推奨はこれ**

### 案C: 解像度は変えず、パレットとディザリングだけ直す（最小コスト）

低解像度化はせず、色設計と芝の質感、スタンド、ネットだけを原作に寄せる。

- 効果: 体感で「かなりマシ」にはなるが、輪郭のなめらかさは残るので**16bitには見えない**
- コスト: 小（定数と描画関数の修正のみ、1日以内）
- 位置づけ: 案A/Bをやるとしても**先にやっておく価値がある**（パレットは共通の土台）

### 3-2. 私（Claude）がピクセル配列を書く — 正直な自己評価

**やり方**: 現在のベクター描画をやめ、パレットインデックスの文字列配列で1ドットずつ定義する。

```ts

  '....hhhh....',
  '...hffffh...',
  '...hf..fh...',   // h=髪 f=肌 j=ジャージ …

```

**できること（自信あり）**
- 機械的な作業としては完全に可能。パレット統制・左右反転による方向生成・

## 4. ドッター向け発注仕様書（ドラフト）

### 案件概要
ブラウザ向け縦スクロールサッカーゲームの選手スプライト。
16bitコンソール風のドット絵。**既存の商用ゲームの模写・トレースは不可**（完全オリジナル）。

### 視点
斜め見下ろし（3/4俯瞰）。カメラは地面から見上げ角のゆるい位置にあり、
**立っている人物を斜め上前方から見た姿**。真上visionでも真横でもない。

### 必要なアセット

| 項目 | 仕様 |
|---|---|
| サイズ | **大 32x32px** / **小 16x16px** の2段（キャンバス寸法。人物の実高さは大28px・小14px前後） |
| 方向 | 8方向（上・右上・右・右下・下・左下・左・左上）。**左右対称なので実作画は5方向で可**（残りは反転） |
| アニメ | 走行4フレーム（接地→通過→逆接地→通過）＋ 静止1フレーム。可能なら キック2フレーム / スライディング2フレーム |
| 色数 | **1スプライト15色以内**（SNES準拠）。うち「ジャージ主色」「ジャージ副色」「短パン色」の3色は**差し替え可能な独立インデックス**にすること（チーム16種を色替えで作るため） |
| 接地点 | キャンバス**下端中央**（足元が原点） |
| 背景 | 完全透過 |
| 追加 | ゴールキーパー用（別ジャージ・手袋）を同仕様で1セット |

### 納品形式
- PNG スプライトシート（横方向＝アニメフレーム、縦方向＝向き）
- 使用パレットの一覧（HEX）
- 可能なら Aseprite の元データ

### 参考として渡すもの
- 本リポジトリの `docs/screen-geometry.md`（カメラの俯角・選手の見かけサイズの実測値）
- 現在のゲーム画面キャプチャ（サイズ感の参照用）

### 見積り依頼時の注意
「8方向×5フレーム×2セット（フィールド/GK）＝ 実作画 50枚相当（反転含めて80枚）」
という規模感で相談するとよい。

## 5. 選手以外のビジュアル要素の改善案

### 5-1. 芝

| 項目 | 現状 | 改善案 |
|---|---|---|
| 色 | `#1c6636` / `#237943`（暗い青緑） | **`#76ae4d` / `#83b453` 前後**（明るい黄緑）へ。実測に基づく |
| 縞の向き | 横縞（Y方向の帯） | ~~縦縞（長辺方向、消失点へ収束）へ変更~~ **【2026-08-17 訂正・撤回】** |
| 縞のコントラスト | ΔG=19 と強め | 原作は ΔG≈6 と**かなり控えめ**。落とす |
| 質感 | 平坦な単色3色 | ~~ディザリング（2色の市松/バイヤーパターン）でノイズ感を出す~~ **【同上・撤回】** |
| 空気遠近 | 遠方を暗くする | **遠方を明るく**（白へ寄せる）へ反転。原作は遠方 `#9acd6c` |

**【2026-08-17 訂正】縞の向き・ディザリングの2項目はユーザー実機確認で撤回された。**
V-4実装時は「原作は縦縞」と判断してX軸分割+ディザリングを実装したが、ユーザーが
GitHub Pagesで確認した結果「芝が市松模様のモザイクに見える。原作はこうなっていない」
「縞は横方向(タッチラインと平行、奥行き方向に交互に切り替わる帯)」との指摘を受け、
Y軸(奥行き)分割の単色帯へ差し戻した。空気遠近(遠方を明るく)は維持しつつ、
帯ごとに`family.near`→`family.far`を滑らかに補間することで市松感を出さずに実現している
(詳細は `src/render/pitchPerspective.ts` の `drawStripeBands` とHANDOFF.md 22周目)。

### 5-2. スタンド・観客席

- 現状は暗い段＋わずかなドット、さらに遠方かすみで潰れてほぼ黒
- 改善: **明るい群衆**（白・水色・肌色・赤の細かいドットを高密度に）へ。
  原作は `#c9dbdb` `#c14931` `#ffffff` 系。段階1で入れた暗色かすみは、
  スタンド帯には掛けないようにする

### 5-3. 広告板

- 現状は暗い帯＋細いストライプ
- 改善: **白地に色ブロック**の帯へ。文字までは不要（読めないサイズ）だが、
  色の並びがあるだけで「スタジアム」の情報量が出る。実在企業名は使わない

### 5-4. ゴールネット

- 現状は縦4本＋横2本
- 改善: **縦横とも細かいメッシュ**（縦8〜12本、横6〜8本）にし、面として見えるようにする。
  低解像度化する場合はドットの点描でメッシュを表現するのが原作的

### 5-5. 全体の色設計（16bit機の色数制限とディザリング）

**SNESの制約**: 15bitカラー（各チャンネル5bit = 32段階）、スプライト1枚あたり15色＋透明。

再現方法の案:
1. **固定パレットを定義する**（48〜64色程度）。すべての描画をこのパレットの色だけで行う
   → 色の統一感が出て、これだけでも「まとまった絵」に見える
2. **各チャンネルを5bitに量子化**（`v & 0xF8`）してから使う
   → SNES特有の「微妙に転んだ色」の質感が出る
3. **グラデーションはディザリングで**（現在の空のような多段階の塗り分けをやめ、
   2色の市松模様やバイヤーマトリクスで中間調を作る）
4. 実装方法は「描画時にパレット色だけを使う」方式を推奨。
   画面全体を後処理で量子化する方式は、240x360でも毎フレーム8.6万画素の処理になり
   **60fps維持のリスク**があるため避けたい

## 6. 推奨する進め方（案）

1. **まず案C（パレット・芝・スタンド・ネット）を実施** — 低コストで効果が大きく、
   後続のどの案とも競合しない土台になる
2. **並行して素材調達の判断**（外部素材 / 私が書く / 外注）
3. **その後 案B（ワールドのみ低解像度化）** — スプライトが決まってから行う方が手戻りが少ない

段階制の開発順序（CLAUDE.md）との関係: これは段階1（見た目の土台）の延長にあたる作業で、
段階2（保持時の操作感）とは独立して進められます。ただし**同時に走らせると
「操作感が変わったのか見た目が変わったのか」の切り分けができなくなる**ため、
段階2の手触り評価を先に終えるか、明確に順番を分けることを推奨します。

### A-3. LPC系という選択肢（組み合わせ運用）

[Universal LPC Spritesheet Character Generator](https://github.com/liberatedpixelcup/Universal-LPC-Spritesheet-Character-Generator)
はパーツごとにライセンスが異なり（CC0 / CC-BY 4.0 / **OGA-BY** / CC-BY-SA / GPL）、
**CC-BY-SA と GPL のパーツを選ばなければ継承義務ゼロで生成できます**。
`shortsleeve` シャツ + `shorts` + `socks` でサッカーキットが組め、クレジット一覧も自動出力されます。

- 4方向しかない弱点は [LPC runcycle and diagonal walkcycle](https://opengameart.org/content/lpc-runcycle-and-diagonal-walkcycle)
  （**OGA-BY 3.0 を選択可＝継承なし**）の斜め4方向で補える
- ただし **64x64 は本作の縦スクロール視点には大きすぎる可能性**があり、縮小の是非を要検討
